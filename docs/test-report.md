# 电商订单系统最终测试报告

2026-10-27 发布前复核：8 项接口与并发回归测试全部通过。 以下保留原测试环境与历史性能记录；本次未重新执行正式性能压测。

## 1. 测试对象

第一版订单 API，覆盖商品、库存、购物车、下单、模拟支付、订单取消、幂等控制和操作审计。

## 2. 测试环境

- Python 3.12
- Flask 3.0.3
- SQLite（测试使用临时数据库）
- pytest 9.1.1
- 执行命令：`python -m pytest`

## 4. HTTP 性能检查

测试命令：`python scripts/load_test.py --requests 100 --concurrency 10`，请求本地开发服务的 `/health` 接口。

| 指标 | 结果 |
|---|---:|
| 请求数 / 并发数 | 100 / 10 |
| 成功率 | 100%（100 个 200） |
| 吞吐量 | 88.32 请求/秒 |
| 平均耗时 | 78.94 ms |
| P50 | 22.87 ms |
| P95 | 756.87 ms |

以上是当前开发机、Flask 开发服务器和 SQLite 条件下的基线数据，只用于回归对比，不代表生产容量上限。

## 5. 已验证场景

1. 下单扣减库存，支付幂等，已支付订单禁止取消。
2. 相同幂等键重复下单只生成一个订单，不重复扣库存。
3. 非法数量、库存边界、空订单参数校验。
4. 取消订单恢复库存，并写入操作审计记录。
5. 未登录访问和管理员越权访问返回统一 401/403。
6. 管理员创建客户账号、重复用户名和弱密码校验。
7. 10 个并发会话抢购 5 件库存时，5 个成功、5 个库存不足，最终库存为 0。
8. 空 SKU 和空商品名称被拒绝，缺陷 BUG-001 已修复并回归通过。

## 6. 持续集成

项目已配置 GitHub Actions，在 `push` 和 `pull_request` 事件触发时执行：

```text
python -m pip install -r requirements-dev.txt
python -m pytest
```

CI 使用 Python 3.12 和 Ubuntu runner；本地回归与 CI 使用同一条 pytest 命令，减少环境差异。

## 7. 当前结论

核心订单闭环已具备可运行、可回归验证的基础，可用于本地功能与回归验证。当前仍属于 MVP：没有真实支付、发货、退款和订单分页。并发用例证明了当前事务下不会超卖，但还不是生产容量压测；后续可补充分页查询和基于真实服务进程的压力测试。
